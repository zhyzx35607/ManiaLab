# 钢琴声部分组：上下文与 rest 构图修复

2026-11-09。已复现并修复研究流程中一处确定的观察图错误：没有未来起音时，rest 关系会错误连接到当前图的全部音符。**修复消除了错误连接，但固定权重的分组质量有改善也有退步，上下文敏感性仍然明显。** 这次没有重新采音、校准 Timing、训练权重或导出成谱，未改变应用默认行为，也不作为音乐验收。

本实验承接[钢琴声部适配与实际导出](piano-stream-research-2026-11-09.md)，按[上下文协议](piano-stream-context-protocol.md)和[rest 修复协议](piano-stream-rest-protocol.md)执行。公开[机器报告](piano-stream-context-research-2026-11-09.json)包含身份、汇总及逐曲统计，不包含音频、逐音符、表达 ID 或研究权重。

## 输入和实际核验

比较两套已冻结流程：原模型原候选、epoch 5 适配模型扩候选。使用 16 份 validation 乐谱缓存，每份最多前 16 个有音符小节；分别使用原音长 clean 和整小节延音 whole，比较完整缓存与最多四个有音符小节的窗口。延音先在完整输入上冻结再切窗，保证同一音符的起音、音高、音长、特征及候选连接一致。完整缓存并不代表整首真实演奏，标签仍是符号乐谱的 `(staff, voice)`。

上下文实验有 64 个“模型×曲目×输入”case，每个包含两种上下文；rest 实验先逐数组复现这些原预测，再对同一输入只过滤错误 rest，使用官方过程重建反向边。两次实验都没有读取 test 数组或重新选择模型。另使用冻结的《樱花草》1557 个钢琴候选，按既定 74 BPM、Offset 178 ms、四细分和 22.5 ms 提前量核对图输入，未读取作者 Reference 或成品音符。

汇总脚本核验了两次实验的执行快照、rest 使用的四个辅助脚本快照、干净上游提交、原始/适配权重、manifest、16 份 validation 缓存、音频分析与图输入身份，以及 rest 的 152 个产物 SHA256。还从逐曲数据重新计算汇总，交叉检查 rest 的原始分数与 context 实验一致。rest 完整运行记录耗时 97.81 秒，成功结束。

## 错误是什么，修复做了什么

上游在某个音尾之后寻找最早的未来起音。如果没有未来起音，但还存在其他更晚音尾，差值数组会全部成为无穷大；随后“等于最小差值”的判断选中全部节点，包括已经结束、正在持续及源节点自身。删除条件为 `onset[dst] <= end[src]`，其余观察边、候选边、特征、音符和权重保持不变。

最小控制检查了无未来起音、多个同时最早未来起音、音尾接起音、单音和同尾输入。修复后所有 rest 均指向严格晚于源音尾的最早起音，合法同起音和弦目标完整保留；连续窗口的观察图等于完整图在对应节点的诱导子图。单音/同尾控制使用最小手构图，只验证过滤器，不声称覆盖上游完整特征构建。

《樱花草》完整图有 583 条 rest，均合法；原窗口图有 2782 条，其中 2244 条是错误新增边，同时正常省去了 45 条跨窗连接。修复后窗口图剩 538 条合法 rest，错误新增和内部漏边均为零。两套模型的整曲预测逐数组不变；窗口预测发生变化。因此这一修复不能解决此前整曲导出本身存在的所有问题。

## 验证集：不能把修复等同于模型提升

指标为同小节内成对同声部分组 F1；逐曲变化按同一指标统计，每行总计 16 曲。这里的“完整”指最多 16 个有音符小节的缓存。

|模型|输入|上下文|修复前 F1|修复后 F1|改善／相同／退步|
|---|---|---|---:|---:|---:|
|原模型|clean|完整|0.89001|0.89017|2／14／0|
|原模型|clean|四小节|0.88038|0.88081|1／14／1|
|原模型|whole|完整|0.53466|0.53542|1／15／0|
|原模型|whole|四小节|0.52464|0.52460|0／15／1|
|适配|clean|完整|0.88358|0.88114|1／14／1|
|适配|clean|四小节|0.87523|0.87449|0／15／1|
|适配|whole|完整|0.81847|0.77703|0／15／1|
|适配|whole|四小节|0.79296|0.79422|1／15／0|

最明显的退步来自 `beethoven_piano_sonatas_08-1` 的适配 whole 完整输入：单曲 F1 从 0.86521 降至 0.75138，FP 从 362 增至 1513，FN 从 1790 增至 2553。该组只有这一曲下降，但它的音符对较多，汇总下降较大；逐曲宏平均从 0.78801 降至 0.78090。错误连接确实应该移除，但这份旧权重在修正后的输入上并未保持同样表现，不能隐去这项退步。

clean 完整图有 2 份谱含错误 rest，共移除 2551 条；whole 完整图有 1 份谱含错误 rest，共移除 6020 条。四小节输入分别在 3／2 个窗口移除 504／1008 条。这些是同一输入的构图数，两套权重共享，不能相加后宣称覆盖更多音符或更多曲目。

移除错误边只解释了部分差异。修复后的适配模型仍有 34 个 staff 分类翻转、1134 对组件关系变化，以及 141 个 components 表达长短翻转。正常跨窗的 240 条 consecutive、51 条 during、45 条 rest 仍存在于整曲图而不在窗口图；GraphNorm 的归一化范围和后处理上下文也仍不同。本轮不能把残余差异全部归因于 GraphNorm，也不能凭更少翻转判定哪种上下文更符合音乐。

单独看修复对四小节表达的影响：原模型 staff 有 7 个长变短、22 个短变长；适配 staff 为 2／5，适配 components 为 11／27。适配 components 的表达长条数从 521 变为 537，而整曲保持 530。数字既不表示正确 LN 数量，也不等于最终谱面数量：这些只是选音、占轨和定轨之前的表达输入。

## 后续边界与重现

本轮支持修复构图语义，并证明窗口截断不能被简单当作无害的推理实现细节。它不证明音频采音、踏板/松键识别、稳定旋律身份、跨小节乐句或最终 LN 手感已经解决。其后已完成[观察边与归一化的独立对照](piano-stream-context-factors-2026-11-09.md)：在已测输入上，两项同时改变可复现逐窗结果，且存在交互；这仍不支持按某一组分数直接切换产品默认。下一步应检查跨小节身份和乐句目标，再决定如何用修正后的图训练。

使用 `.venv/Scripts/python.exe scripts/summarize_piano_stream_context.py --output <新JSON路径>` 可以重新核验并汇总现有本地结果，不运行模型。公开 JSON 保留实际执行脚本哈希与当前源码哈希。运行结束后，主线程修正了“窗口没有删边时不应比较包含全图统计的审计 JSON”这一条件断言，并允许上下文脚本仅有换行格式及文件末尾空行的差异，以兼容提交时的空行清理；其他字符仍必须逐项相同。原成功运行快照没有覆盖，以上结果来自该真实快照，不归功于事后修订。
