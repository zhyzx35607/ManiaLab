# 实际训练与验证语料的延音线损失

在 173 份固定 train/validation 原谱中，本次完整覆盖 151 份；这 151 份的处理后窗口全部与旧缓存逐字段一致。在相同前 16 小节窗口中，预处理删除了 647 条同小节已导入延音线，另按原设计删除了 559 条跨小节延音线，共新增 1,206 个 note-array 事件。这些数据证明已发现的问题确实进入了训练输入，不仅存在于自造例。

另外 22 份在审计检查阶段出现“tie 指针端点不在 `iter_all(Note)` 集合中”的错误，未计入完成统计。随后只读类型诊断确认：165 个集合外端点全部是已注册的 `GraceNote`，在包含子类的音符集合和时间线对象中均可找到，且记谱时长为零。原审计默认不遍历子类，因此这里是审计范围缺口，不是已证实的悬空指针。旧统计和 22 份错误记录保持冻结，不能静默补入或称 173 份全部通过。

这 22 份原 XML 合计也有 165 个带 sound tie 的 grace note，没有发现带 sound tie 的 cue/rest；所有 note 均无显式 ID。数量相同不能替代逐音符身份核验，所以诊断没有把 Partitura 自动 ID 猜配给 XML 节点，也不证明这些 tie 配对或声学时间本身正确。[端点类型汇总](piano-corpus-tie-endpoints-2026-11-09.json)只解释覆盖缺口，尚未实现 tied grace 的处理。

窗口统计直接使用原缓存保存的 16 组小节边界，并从完整处理后数组复现原准备器的先选小节、再过滤非正时长与钢琴音域外事件、再排序的流程。151 份 notes、measures、measure_bounds 均精确相同，避免了把不同段落或不同过滤口径混在一起比较。69 份窗口存在同小节延续丢失，103 份窗口出现新增事件；这些分母均为已完整覆盖的 151 份。

完整原文件的影响更大，但不能与 16 小节训练窗口混用：

| 完整文件口径，仅 151 份覆盖文件 | train | validation | 合计 |
| --- | ---: | ---: | ---: |
| 已导入 tie | 7,910 | 1,565 | 9,475 |
| 删除同小节 tie | 2,880 | 1,022 | 3,902 |
| 删除跨小节 tie | 5,029 | 542 | 5,571 |
| 保留原 tie | 1 | 1 | 2 |
| 新增 note-array 事件 | 7,909 | 1,564 | 9,473 |

这些覆盖文件中，导入器给出的 tie_next/tie_prev 双向关系相互一致，处理后没有新增关系；118 份完整文件出现同小节关系丢失。以上仍然只是“已导入后可观察到的关系”：此次没有逐条核实源 XML tie 声明，也无法统计已知并行同音导入漏连的数量，更不能将 9,475 当作原文完整延音线总数。

同小节删除与跨小节删除具有不同含义。前者已经由[七个自造控制](piano-bar-identity-research-2026-11-09.md)证实是预处理检查错误；后者是原函数为小节内声部任务特意进行的切分。两者都不应在新的声学采音任务中未经标记地充当重新起音。note-array 时长也只是记谱持续范围，不能直接作为物理松键、声音消失或 LN 放手标签。

本次先执行 `corpus-ties-v1`，发现审计器在每个音符上重新构建同一小节映射，首文件耗时约 59 秒。该初次运行在 3 条记录后主动停止，保留了两份成功结果和一份异常，没有完整总报告。随后仅将映射构建移到每 part 的循环外，冻结[等价加速协议](piano-corpus-ties-fast-protocol.md)并另开 `corpus-ties-v2`，约 546.49 秒完成所有文件。新旧前三条详细结果除 elapsed_seconds 外完全一致，两份成功文件的原/处理后数组也逐字段一致；没有混用初次结果或覆盖原目录。

公开汇总从 327 个新产物独立重算已保存关系、事件多重集合和时长变化，核验 173 份所选源文件及缓存哈希，并验证处理后窗口事件键与原缓存一致。逐音符、数组和原始 warning 内容仅存于本地忽略目录。源文件、旧缓存与上游源码未改，没有载入模型、训练权重或启用应用行为。
