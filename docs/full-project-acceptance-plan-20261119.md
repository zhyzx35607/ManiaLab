# ManiaLab 全项目验收计划

更新：2026-11-19。目标不是用一次大重写替代验收，而是沿实际用户工作流补齐可复核证据，只在发现可复现的高风险问题时修改实现。

## 验收目标

最终交付分为两个独立结论：

1. **工程验收**：用户导入、分析、Timing、声部/段落表达、候选生成与编辑、保存/取消、OSU/OSZ 导出、Windows 运行及发布能力边界均有与风险匹配的验证；没有未解决的 P0/P1 工程问题。
2. **音乐验收**：真实钢琴起音、6–10K/LN 可玩性以及独立歌曲的采音、段落、声部和 LN 表达有独立真人记录；问题有定位和结论，不以 CI、自动模型分数或参考谱逐音匹配替代听感。

工程门槛通过而真人证据未回收时，项目只能标为“工程验收通过、音乐验收待完成”，不能标为整体完成。

### 阶段 2：跨模块工作流与架构契约

**状态：进行中。**

沿 `docs/architecture.md` 的真实数据流逐段核对：

1. 原音频/分离声部及其身份进入采音、缓存和来源证据。

**退出条件：**以上三类材料均有真实参与者结果、锁定回执及汇总；不存在未处置的高影响音准/Timing/声部/LN/可玩性问题。最终报告只发布必要汇总，不提交个人信息或原始评审资产。

### 阶段 5：支持配置、便携交付与许可边界

**状态：Core 已有验证；完整模型 profile 和权重授权未闭环。**

建立公开支持矩阵，逐项说明功能、资源、下载/联网要求、实际验证和发布资格：

- `core`：当前 GitHub workflow 的便携验证 profile。
- `standard`：四/六声部分离、节拍、钢琴/先验及原模型安装器等非 Core 功能。
- `extended`：另含吉他 FL 与 Tsumugi worker。

Core 通过不能推导 standard/extended 通过。对每个要公开支持的 profile，核对真实构建输入、模型身份、最终 ZIP 清单、clean PATH 离线启动、Unicode 数据路径、导入/生成/导出、重启和关停。Demucs checkpoint 在独立再分发授权未核实之前，不把包含它们的 profile 宣告为可公开重新发布；解决方案必须是可核验授权、移除该公开 profile 中的权重并准确降级能力，或另选具备授权且已验证的资源。

**退出条件：**公开支持的每个 profile 都有与其能力匹配的构建和 EXE 验证证据；所有随包模型具有明确来源、哈希和许可依据。旧 Release 单独核查，不把新主线 CI 当成旧包内容证明。

### 阶段 6：最终验收、交接与停止

以同一合并 `main` 提交执行最终证据核对：全量 Python/API、Edge 浏览器流程、静态编译/语法、OSU 官方解码和目标 profile 的真实 Windows EXE 报告；逐项复核问题账本；发布一份最终工程/音乐双结论报告。

**整体停止条件：**阶段 1–3 与阶段 5 的工程门槛通过；阶段 4 的真人音乐门槛通过；没有未解决 P0/P1；工作树干净；报告、CI run、提交和实际 profile 身份能互相追溯。若真人评审或许可材料缺失，停止无证据的代码重构，明确标记“部分验收/待外部证据”，不宣告项目整体完成。除非另有明确发布目标，不自动创建新 Release。

## 变更与范围控制

- 每个修复阶段先有复现或覆盖缺口，再改代码；更新 `docs/PROGRESS.md`，提交、推送、开 PR；Windows PR 检查通过后合并并等待 main run。
- P0/P1 是阻止数据正确性、项目安全恢复、核心流程或公开交付的问题；需修复或有明确风险处置。P2/风格性整理记入账本，不阻断音乐验收也不单独触发重构。
- 不设任意 PR 数量上限，但每个 PR 必须有单一用户影响和可判定的退出条件。最终回归后不继续追逐无关整理；只有新证据显示用户风险时才重开对应阶段。
- 研究继续保持串行；不改正在运行或排队的脚本。研究和模型实验只有在现有冻结证据无法回答具体音乐问题、且先写清对照假设与验收标准时才提出。

## 预计工作量与依赖

阶段 0、1 的本轮导入修复已合并。阶段 1–3 的剩余内容是一次有边界的审计与缺口验证，预计需要若干工程工作段和对应 PR/CI 周期，实际修复数由复现结果决定。阶段 5 是否需要构建 standard/extended 取决于公开支持范围和许可依据。阶段 4 依赖真实评审者和实际 osu!mania 玩家时间，无法由代码代理给出可靠完成日期；参与者开始前可完成其余工程审计，但不能代签。
