# 吉他专用采音应用链路验证（2026-11-10）

源码应用与 `0.1.0-alpha.6-dev.4` 可分发 EXE 均已完成三份真实输入、四种输入/音尾组合的 HTTP 验证。独立审核确认，原浮点声轨和模型逐音证据进入应用后保持完整，默认模型尾不会转成 LN，导出的 6–10K 音符与候选时间和轨道一致。审核同时发现无分段歌曲继承负数模板书签的问题；修复后，源码重新导出的 13 个保存候选及 EXE 新生成的完整 15 份谱均通过检查。

**可分发 EXE 的吉他应用链路复测与独立产物审核已通过。** 测试统一使用人工指定的 **120 BPM / Offset 0 / 1⁄4 细分 / 提前量 0**，用于检查导出与来源，不能当作自动 Timing、实际歌曲对音或 LN 手感验收。

## 已完成的真实输入流程

固定浮点模型证据来自 [hf-guitar-float-results.md](hf-guitar-float-results.md)。首份完整 GuitarSet 录音同时测默认起音模式和显式模型尾模式，两条原生完整声轨测默认模式。HTTP 路由实际完成声轨上传、冷缓存推理、音频/声轨接口、表达方案、6–10K 导出、谱包导出、项目重启、热缓存与取消。

| 输入与模式 | 模型 raw 事件 | 能量过滤后候选 | 6K 导出 / LN | 7–10K 每份导出 / LN |
|---|---:|---:|---:|---:|
| GuitarSet `guitar-00_BN1-129-Eb_comp` · 默认起音 | 128 | 128 | 128 / 0 | 128 / 0 |
| 同一录音 · 显式允许模型尾 | 128 | 128 | 128 / 75 | 128 / 75 |
| 樱花草 · Nova 极弱吉他轨 · 默认起音 | 0 | 0 | 不生成空谱 | 不生成空谱 |
| 有点甜 · HTDemucs6 吉他轨 · 默认起音 | 2521 | 2519 | 2462 / 0 | 2467 / 0 |

《有点甜》的两个低能量候选为 `guitar:fl:168`、`guitar:fl:1403`，独立重算的原曲/声轨局部 RMS 与拒绝门槛确认了相同取舍。该过滤不对吉他音轨单独拉高增益。保存的取舍记录中，6K 的 `represented_by_chord` 为 56、`duplicate_pitch` 为 1；7–10K 分别为 51 和 1，对应表中候选与生成物件的数量差。这些计数不代表已经验证音符正确。

《樱花草》吉他轨的零事件结果沿整个冷缓存、重启和热缓存路径保持为零。表达方案没有伪造 `guitar` 声部策略，未选取更响片段、补造音符或导出空谱来满足测试。两条真实歌曲缺少独立吉他逐音标签，以上数字没有准确率含义。

## 独立核对的范围

审核只读取保存的产物，不加载神经运行时或应用模块。它重新解码原曲作能量比对，逐样点核对 float WAV、导入 NPY 和固定探针输入，核对模型缓存的四个激活头、完整 raw event、候选 trace、音尾资格及两模式缓存身份。四个组合的模型缓存都与对应浮点探针激活逐值相同。

源码原轮导出共 15 份 `.osu` 和 3 份 `.osz`。独立解析实际文件中的红线、物件类型、起止时间、列坐标、排列顺序、同轨重复/重叠以及固定网格；谱包内谱面与单独导出一致，音频字节与导入原音频相同。默认模式全为短键，显式模型尾模式的 75 个 LN 均可追溯到 `model_predicted_offset`，未确认音尾不会获得 LN 资格。

项目只保留最近 8 个候选，因此首个项目最早的默认 6K / 7K 候选已经不在最终 `state.json`。审核没有声称所有 15 份都有保存状态可比：其余 13 份逐音起止/轨道与状态相同；最早两份另用全部 raw 起音量化后的多重集检查，128 个短键全部对应，轨道合法无重叠。

主 HTTP 验证脚本观察了真实停止/重启及取消过程。独立文件审核核对最终热缓存证据、保存的选项及取消项目没有部分分析结果，但不把文件复核描述为又执行了一次重启或取消。

## 发现并修复的书签问题

原轮首个项目的 10 份导出都出现 `Bookmarks:-330001`。原因是新生成谱没有内部段落边界时，`export_osu` 未覆盖 Mapperatorinator 模板中的占位书签。这个错误不改变 HitObjects，却会污染编辑器段落导航。

修复让新生成谱始终写入明确的书签列表；没有内部边界就写空列表，已有谱重新定轨分支保持原谱元数据。原源码 HTTP 结果与缺陷记录均保留，没有改写成“原轮无问题”。

修复后，将原项目的状态和音频复制到独立测试目录，通过真实 HTTP 选择候选并重新导出 13 份 `.osu` 与 13 份 `.osz`。分析入口被禁止调用，任务队列保持为空，没有重新推理：

- 首个项目仍保存的 8 份谱书签全部为空，不再出现负数占位值。
- 《有点甜》的 5 份谱都保留其 12 个实际段落边界书签。
- 除 `Bookmarks` 行外，13 份谱的正文逐字保持不变；起止和轨道与保存候选完全相同。
- 谱包音频字节保持不变，原测试项目与文件未修改。

这次源码重新导出覆盖 13 个仍保存的候选。最早默认 6K / 7K 两个候选未在该轮修复源码上重新导出；后续 EXE 新生成的完整 15 份测试已覆盖它们，书签同样为空。

## 可分发 EXE 的完整复测

真实 EXE 在独立中文数据目录、清理过的 Python 环境变量与系统 PATH 下运行，外部 HTTP/HTTPS 代理指向不可用地址。上述三输入、四种组合全部完成，逐组导出数量与表格一致；声轨上传、冷缓存分析、起止证据、试听、保存、停止重启、热缓存和冷任务取消均通过 HTTP 验证。独立审核不重新执行模型或运行应用，只核对已完成的产物与报告。

独立审核核对 EXE、音频 worker、模型文件及 manifest 中的 67 个源码文件身份，并重做三输入的浮点 PCM、四头模型缓存、raw trace、能量过滤和所有导出检查。15 份 `.osu` 与 3 份 `.osz` 全部通过，未发现负书签。首份录音十份谱的书签精确为空，《有点甜》五份谱均保留对应的 12 个段落边界；这里检查了完整列表，不能用删光书签来通过验证。

15 份便携版谱面与最初源码结果逐字比较，除 `Bookmarks` 行外全部相同；其中原状态仍保存的 13 份，与修复源码通过 HTTP 重新导出的文件逐字相同。三个谱包的成员名称、音频字节保持一致，谱面也只允许书签行发生修正。两个被原项目候选数量上限淘汰的早期候选，仍按上文的方法核对全部 raw 起音量化多重集，没有声称恢复了不存在的历史状态。

| 输入与模式 | 本机冷分析耗时 | 重启后的热缓存耗时 |
|---|---:|---:|
| GuitarSet · 默认起音 | 16.95 秒 | 1.07 秒 |
| GuitarSet · 显式模型尾 | 16.80 秒 | 1.27 秒 |
| 樱花草 · Nova 极弱吉他轨 | 163.37 秒 | 5.43 秒 |
| 有点甜 · HTDemucs6 吉他轨 | 113.05 秒 | 4.67 秒 |

这些时间是这台机器的实际运行记录；热缓存复用了相同输入与设置的证据，不是重新完成一轮模型推理。耗时本身不代表音乐质量，也不保证另一台电脑的速度。

## 尚未取得的结论

本轮完成的是吉他专用采音到源码及可分发 EXE 导出的链路检查。75 个可追溯模型尾不等于 75 个艺术上合适的 LN；固定 120 BPM 下落线也不证明歌曲自动 Timing 正确。《樱花草》的零吉他输出不表示其他乐器采音已经达到用户 Reference 水平。完整乐器/段落理解、实际 Timing 和最终键型质量仍须各自验收。
