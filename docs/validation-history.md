# 验证记录

测试环境：Windows 10 x64、Python 3.12.10、Intel i5-9600K、CPU 推理。记录日期：2026-11-07。

## 用户真实音频补充验证

收到用户的《有点甜》MP3 后，逐位复现了 alpha.2 的 210.00073 BPM / 118.373ms 和参考工具的 209.998 BPM / 91ms。参考工具输出前存在固定减 22.5ms 的步骤，已通过只改该常量的本地测试副本确认。固定 210 BPM 时，参考结果为 93ms，去除该补偿后为 115ms；alpha.3 为 117ms。尚未确认该工具补偿的设计用途及对应播放器环境。

真实全曲生成 1,465 个物件、310 个 LN，回读导出的 1,775 个端点全部落线。另制作保持轨道和 LN 长度相同、只相差 24ms 的 93 / 117ms 对照谱。完整记录见 [同文件调查](timing-investigation-165340.md)。以下 alpha.3 发布时“未取得相同音源”的描述为历史状态。

## 0.1.0-alpha.3 对音与落线修复

用户反馈 210.00073 BPM、118.373ms Offset（参考工具为 91ms），以及短键和 LN 尾端离线。代码复查确认 alpha.2 的吸附只处理窄容差内的物件：210 BPM 四等分时实际仅约 16.43ms，超出者原样通过；拍线不稳定时整个吸附停用，但仍可生成、导出。LN 尾端的单向容差也导致大量未量化尾端。上一版的“通过”只覆盖了这些旧规则，并未证明完整落线。

本版自动 BPM 按常见分数或整数整理，再固定 BPM 重新拟合整数 Offset、重新评分。所有生成端点完整量化，导出回读实际 `.osu`，按实际红线检查误差。自动 Timing 不可靠时停止生成；手动参考 Timing 必须试听确认。旧候选不能直接导出，重新分析会清除其活动状态但保留列表。改 Timing 后局部重写会阻止混合拍线。

另修复导出模板的编辑器细分固定为 4 的问题：选择三等分时，`BeatDivisor` 也输出 3，避免三连音谱面在编辑器默认四等分线上看起来离线。

`python -m pytest -q`：63 项通过，包含原有测试和新回归：

- 210.00073 → 210，保留接近 .25 / .333 / .5 / .667 / .75 的数值；手动特殊 BPM 保留。
- 固定 210 BPM 重新拟合 91ms Offset；不沿用更改前的相位。
- 105 / 210 BPM + 91ms、166.667 BPM + -91ms 三连音、174.5 BPM 的完整导出端点检查。篡改 LN 尾端 8ms 后，导出明确失败。
- API 在 6–10K 下输入 210 / 91，逐个读取导出物件和红线；同时验证未知 Timing、旧候选、局部改 Timing 与重新分析状态。

源码 Edge / Playwright 三组脚本通过：`ui_grid_smoke.cjs`、`ui_timing_smoke.cjs`、`ui_smoke.cjs`。实际页面粘贴 210 / 91 后导出的 10 个端点全部通过，最大舍入误差 0.428572ms；137 BPM 显示为整数，重新估计 Offset 为 346ms（该合成音起点为 347ms）。LN 比例 100% / 0% / 60%、导出谱包、严格重定轨、候选状态和手机宽度通过，无页面脚本异常。

PyInstaller 独立 EXE 使用独立数据目录、端口 8978，运行同样三组页面测试，结果一致；另外实际导出三连音并检查 `BeatDivisor: 3` 与每个端点。分析 JSON 可在未生成或重新分析清除活动候选后下载，用于反馈 Timing 候选、原始拟合值和起音时间，不包含音频文件。

### Offset 对比及未解决部分

用相同的 44.1kHz WAV 对比用户提供的 Timing Analyzer v0.32.4 alpha（固定输入 105 BPM）和本版。每个样本 60 秒，物理起点 91ms；700Hz 衰减音，改变音量渐起时长。用于研究时标差异，不能代替真实歌曲验收。

| 渐起时长 | ManiaLab Offset | Timing Analyzer Offset |
| ---: | ---: | ---: |
| 0ms | 90ms | 67ms |
| 10ms | 93ms | 72ms |
| 40ms | 95ms | 79ms |
| 80ms | 95ms | 83ms |

差值随信号变化，不能对 ManiaLab 统一减 27ms。尚未获得用户网易云下载的《有点甜》的相同音源，所以 **118.373ms 与 91ms 差异的真实原因仍未验证**。本版没有宣称自动 Offset 已达到可靠制谱标准；落线、声音起点准确性与音乐表达是三个分别需要验证的条件。

并行运行测试和浏览器时，一次 pytest 输出过 Windows access violation 堆栈但继续完成 63 项、退出码 0；单独重跑全套未复现。保留该观察，不把退出码单独视为无异常证据。

增加弱细分、开头静音、120→137 BPM 变速测试；变速样本必须报告不稳定并停用自动吸附。还覆盖人工确认后的吸附、30ms 移动上限、LN 音尾不能延长，以及真实 HTTP 导出红线与音符一致。

用户提供的 `分析Timing.exe`：Timing Analyzer v0.32.4 alpha，SHA256 `8EE122F8E6B3F7A87177A655E6DBA0904C961F598C68E64075AC7A2E17BB9F1F`。实际命令行 `TimingAnlyz.exe <file> 0`，需 32 位 BASS.dll。使用官方 BASS 下载中的 DLL 在隔离测试目录运行；100 秒、44.1kHz、137 BPM 的相同脉冲样本，返回 BPM 137.000、Offset 322ms；已知物理起音相位为 347ms。因此该程序可作比较，不能把其 Offset 无条件当成真值。EXE 和 BASS 不随 Release 发布。

### LN 与定轨

- 25%、50%、75%、100% 的可行候选集，LN 数量达到目标；0% 输出短键，选中的起音数量保持不变。
- 不可行目标返回可达比例；未来满轨和弦、同时 LN 上限与释放间隔进入整数约束，不靠删除后续短键达标。
- 修复模型在释放前误触发新起音，导致单个持续音分裂为 LN 加短键的问题。原 30 秒合成测试从只检查“存在匹配音”加强为候选数量也必须等于 5；已通过。
- 5 份公开 10K 谱面、6528 个物件重新完成 6 方案定轨，原始起止/类型/音效字段和 TimingPoints 全部保留，无同轨冲突。耗时见 JSON；没有人为等待。

### 页面实测

源码版 Edge / Playwright 实测 LN 100%→0%→60%，结果分别为 100%、0%、60%；137 BPM 测试音频的页面结果为 136.99977，9 段拍线检查均无异常。节拍器启动、倍半速、手动修改后清除确认状态均通过；未捕获页面 JavaScript 错误。浏览器截图检查了 LN 指标、拍线控制和移动布局。

### 参考项目与实际边界

Torosu 克隆在 `D:\project\references\Torosu`，固定 commit `b283791f46622b0dd1f47f53afa10bd62d700e66`。阅读了 `key_converter.rs`、`analysis/layout.rs`、`analysis/patterns.rs`、`timing.rs` 与 `fln_converter.rs`。采用显式双手布局、LN 释放状态、局部负担和多个候选评价的设计思路；未把其全 LN / Inverse 的“延长到下一音前”当作音乐持续证据。

## 原模型集成

可选安装器已在隔离环境安装 CPU PyTorch / torchaudio 2.9.1 和上游推理依赖，下载固定 revision 的 V32 `gamemode=3` 权重。通过上游实际 `inference.py` 在 CPU 上完成 8 秒合成片段的 timing / map / SV 生成，导出后通过新定轨器回读检查。

这次原模型输出只有 1 个完整 LN，并报告片段末端的另一条 LN 没有配对结束事件。上游会丢弃该不完整 LN；ManiaLab 会保留并展示原模型警告。该结果证明原模型入口能运行，**不证明制谱质量足够好**，也说明“原模型权重接入”和“改善 LN 理解”是两项不同的工作。
