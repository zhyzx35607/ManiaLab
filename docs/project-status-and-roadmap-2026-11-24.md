# ManiaLab 当前状态与重规划

更新：2026-11-25。状态依据本地 `main`/精确 release tag、GitHub Release、随包验证说明和源码清单核对。本次只对生成的合成音运行便携/worker 校验，没有读取 ignored 用户音频、谱面或逐曲研究数据。

## 结论

ManiaLab 已经是可体验的 6–10K osu!mania 本地制谱工作台，不是尚未成形的原型。`0.1.0-alpha.6-dev.26` Extended Windows x64 预发布包已于 2026-11-24 发布。工程主流程和便携启动检查覆盖较完整；真实音乐质量、下载体验、扩展模型权利和多机安装体验仍未闭环，所以目前应称为“公开试用、等待真实反馈”，不能称为稳定完成。

最优先的问题有两个：普通用户必须处理 12 个分片才能拿到 1.22 GiB 的包；包内模型和隔离 worker 运行时占了绝大部分体积。其次是收回真实听审/试打结果。清理测试文件数量不能解决这三个问题。

## 目前已经具备的产品流程

用户可以导入音频或已有 osu!mania 谱面，运行可用的声部分离与采音，核对 BPM/Offset 和音符来源，选择预设或编排方案生成候选，编辑候选，再导出 `.osu`/`.osz`。应用还支持区域重写、候选历史与恢复、局部音频试听/波形定位、6K–10K 键型和 LN 设置，以及一次导入 2–10 首、最多并行分析 2 首的批量流程。

已完成的重点是可用工作台、数据和候选身份保护、任务取消与资源清理、导出一致性、浏览器工作流，以及 Core/Extended 便携包的构建验证路径。模型研究脚本仍存在很多，但研究结果不会自动进入默认产品行为。

## 体积从哪里来

dev.26 组装 ZIP 为 `1,310,888,430` bytes，即 1.31 GB（十进制）或约 1.22 GiB；按 ZIP 目录统计，解压后约 `2,714,858,795` bytes（2.53 GiB）。组装期间，分片和临时 ZIP 会同时存在，约需 2.44 GiB 空间；保留 ZIP 并解压后，建议预留至少 4 GiB。

本地已验证 ZIP 的压缩体积约 85.3% 来自随包 `assets`。最大的内容是 Demucs 高质量权重、钢琴 ONNX、吉他 FL、Beat This、Tsumugi 贝斯/其他伴奏权重和六声部模型。2026-11-25 已在构建器加入安全去重：只有 app 根目录的 `torch_cpu.dll` 与音频 worker 内副本大小及 SHA-256 完全相同时，才从新构建 app 目录删除根副本；隔离 worker DLL 保留，Core profile 为 no-op。单元测试覆盖匹配删除、不匹配保留、worker 缺失保留、根 DLL 缺失 no-op、链接拒绝。新构建器生成的 Extended 包完成 portable verifier、four-piano 合成分析/导出、worker 关停、CRC 和 archive manifest 清单校验。新构建 ZIP 为 `1,235,330,669` bytes；相对未去重 dev.26 包减少 `75,557,761` bytes（5.764%）。这属于基于 `main` 源码重新构建的验证产物，不是已发布 dev.26 ZIP；新功能须随未来版本 tag 发布。

12 片 `.ps1` 下载器会同时启动 12 个隐藏的 `curl.exe`。窗口只显示完成了几片；某片中断后重试会删掉它的临时下载并从头下载。当前审计环境对一个分片的 HEAD 请求得到 HTTP 200，这只证明该环境能访问该分片，不能解释用户遇到的失败。失败的具体位置/报错还需要用户提供。

## 项目“臃肿”的实际构成

| 内容 | 数量/大小 | 判断 |
| --- | ---: | --- |
| Git 跟踪 `tests/` | 当前主线 264 个文件（238 个 Python、21 个 CJS、5 个 PEM 夹具） | 没有证据支持按数量删除 pytest；CI 会运行 Python 与浏览器回归。本轮只迁移一个有效断言并移除旧 runner。 |
| Git 跟踪 `scripts/` | 当前主线 422 个文件（395 个 Python、23 个 CJS） | 研究、数据准备和报告工具混在一起；脚本索引明确要求保留历史路径，暂不批量移动/删除。 |
| Git 跟踪 `docs/` | 当前主线 380 个文件（299 个 Markdown、77 个 JSON） | 研究证据有价值，但导航入口太多。`docs/PROGRESS.md` 约 365 KB / 2,204 行，把当前状态与长期历史混在一页；它只占 docs 体积约 2.3%，主要是阅读负担。 |
| 本地 ignored `build/` | 8,687 个文件，约 7.68 GB | 主要是不同 run 的构建、发布 ZIP、检查报告和缓存；需按 run/保留策略盘点，不能整目录清空。 |
| 本地 ignored `assets/` | 4,993 个文件，约 2.20 GB | 模型和运行资源；不能按缓存清理。 |

以上文件数是本轮改动前的 `70a52a4` 主线基线；本轮增加 1 个状态路线图、移除 1 个旧 runner，最终将为 docs 381、scripts 421、tests 264。

本轮测试清理只移除了无法在干净 checkout 运行、依赖 ignored Playwright/素材、且主流程已有 CI 浏览器覆盖的旧通用 runner `scripts/ui_smoke.cjs`。它唯一有用的窄屏横向溢出检查已迁到 `tests/browser/workflow.spec.cjs`。没有删除 pytest 用例；`ui_grid_smoke.cjs`、`ui_timing_smoke.cjs` 和其他带独有场景/历史复现价值的 smoke 工具暂时保留。

## 重规划顺序

### 1. 先让用户拿得到包

为下一次发布更新下载器：最多 1–2 路并发、显示每片字节进度/速度、支持断点续传、保留已下载临时片、失败时指明哪个 URL/分片、组装前预检磁盘空间并逐片校验哈希。发布验证要在一台干净 Windows 机器上从 Release 页面开始完整跑一次，并记录首个失败点和可恢复性。若 GitHub 允许，优先提供直接下载 ZIP 的入口；分片版保留作网络不稳定时的备选。

### 2. 把首次下载缩到轻量 Core

项目已经有 `core`、`standard`、`extended` 三种打包 profile，资源由 `scripts/package_assets.py` 按清单挑选。Core 主要提供 Basic Pitch；Standard 增加分离、节拍、钢琴及 Mapperatorinator 安装组件；Extended 再加入吉他和 Tsumugi。第一步应从 dev.26 精确 tag 构建并验证 Core，再把它作为轻量下载入口与 Extended 并列提供；dev.23 Core ZIP 约 112 MB，可作基线，新包体积需以实际构建测量。另保留完整离线 Extended 包供愿意一次下载所有资源的用户。

打包优化先验证依赖树和子进程隔离。dev.26 ZIP 中三个同名 `torch_cpu.dll` 大小和 CRC 一致；构建 TOC 显示最外层副本来自冻结音频 worker 依赖，适合优先测试是否可去掉这一份，潜在减少约 75.6 MB 压缩体积。两个 worker 内的重复运行时与 `llvmlite.dll` 可能是隔离设计的一部分，不能直接删除。同步审计没有进入本次 profile 的文件，绝不从全局 `assets` 直接粗暴删模型。第三方权利未核实的权重先设为发布门槛，不把“包能构建”当作再分发授权。

### 3. 冻结新增模型功能，回收真实音乐证据

保持当前“导入→分析→校准→表达/定轨→编辑→导出”主流程稳定，暂停没有真人反馈支撑的新模型堆叠。按既有协议回收 84 段钢琴盲听、6–10K/LN 玩家试打、Sweet Waltz 与 Choice 两首独立歌曲的 Timing/声部/段落/LN 评审。先锁定盲听结果再解盲；每个 issue 都要有复测或明确接受结论。工程测试通过不能代替该阶段。

### 4. 让文档与研究代码有明确入口

把本页作为“我现在做到哪”的首要入口；`PROGRESS.md` 继续记近期阶段和可复现命令，历史阶段逐步迁入归档文件，迁移前先盘点 Markdown 锚点并保留兼容链接。给研究脚本补“用途、协议/结果、输入目录、是否进入产品、最近复现状态”索引。历史路径先用兼容 wrapper 过渡，不一次性重命名数百个文件。

### 5. 用覆盖证据继续精简

把自动验证分成三层：每次 CI 的 API/领域与浏览器关键用户流程；发布时运行的 profile/真实 EXE/工件身份检查；仅在有冻结输入和协议时运行的研究/听审工具。只有在确认无人调用、无独有断言、无历史复现价值，并由替代测试覆盖后，才删除一个测试入口。保留故障注入、身份/回滚/取消、OSU/OSZ 往返、真实窄屏和候选来源保护等高风险测试。

### 6. 安全处理本地工作区占用

将 `build/` 视为分 run 的证据仓，而非可随手清空的缓存：保留当前 release 验证、仍被进度记录引用的 artifact 与用户研究输出；只对明确过期、可重新生成且没有引用的目录建立清单后清理。`assets/`、`.venv/`、用户音频、参考谱和模型不随源码瘦身任务删除。

## 何时可以说项目完成

需分别通过工程与音乐两道门槛：工程没有未解决的高严重度状态/导出/关停问题，公开 profile 在干净 Windows 机器可下载、安装和运行且许可范围清晰；真人音乐材料全部完成并且高影响问题已修复复测或明确接受。任一道仍未完成时，都标注为“公开试用/等待验收”，不因 CI 绿灯或 Release 已发布宣布整体完成。
